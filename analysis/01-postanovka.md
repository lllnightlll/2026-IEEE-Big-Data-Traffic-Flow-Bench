# 1. Постановка задачи

## Что это за соревнование

TrafficFlowBench — трек 2 транспортного блока IEEE Big Data Cup 2026. Площадка сдачи — Kaggle. Соседний трек OpenCity идёт на Codabench, у него другие данные, организаторы и призы. Смешивать их нельзя.

Предмет — десять направленных коридоров автомагистралей с шагом 5 минут. Записи синтетические: их породила модель транспортного потока, откалиброванная по реальным детекторам тех же коридоров. Сами реальные записи в релиз не входят.

Смысл бенчмарка не в том, чтобы уменьшить одну ошибку прогноза. Четыре задачи вместе описывают контур центра управления движением: заполнить дыры в датчиках, не нарушить сохранение автомобилей, сказать, куда поедет очередь, и восстановить спрос, который датчики прямо не измеряют.

## Четыре задачи

### State, вес 0.35

Восстановить скорость (`speed_kmh`) и поток (`flow_vph`) в ячейках, которые организатор вырезал из наблюдений. Можно использовать остальной коридор в тот же момент, ту же связь в другие моменты и историю коридора.

Целевые ячейки берутся из шаблона `task1/<panel>/<split>/sample_submission_state.csv`. Пустое значение в файле наблюдений ещё не означает, что ячейка входит в оценку: часть пустот — это горизонт Task 2 и час после него, а часть — негодные детекторы.

Три режима маскирования, каждый календарный день принадлежит ровно одному:

| Режим | Доля пригодных ячеек, вырезанных в этот день |
|---|---:|
| R1 | 20% |
| R2 | 30% |
| R3 | 50% |

День не публикуется трижды. Иначе пересечение трёх масок раскрыло бы ответ.

### Queue, вес 0.30

По 60 минутам истории до момента прогноза `T` (от `T-60` до `T-5`) сказать, на каких связях будет очередь в `T+5` … `T+30`. Это шесть шагов по 5 минут. Строку на самом `T` использовать можно.

Очередь: скорость не выше `0.60 * free_speed`. Метка берётся из истинного состояния, а не из шумного наблюдения, чтобы ошибка измерения не переключала метку у порога.

Окна двух типов, по пять на коридор и сплит:

- `queue_onset` — в истории очереди нет, в горизонте она появляется;
- `queue_ongoing` — очередь уже видна в истории.

В обоих типах очередь в горизонте гарантирована. Ответ «очереди нет нигде» бесплатных баллов не даёт. Начала окон внутри группы `(panel, split, condition)` разнесены минимум на 360 минут.

Коридоры `D12_I405_N` и `D12_I405_S` из Task 2 исключены. В остальных трёх задачах они остаются.

Смотреть записи после момента прогноза для этой задачи нельзя. Это единственная задача с жёстким запретом на будущее относительно `T`.

### Physics, вес 0.15

Отдельной сдачи нет. Оценщик читает скорости и потоки из файла State и сам строит физическую рамку:

- плотность `k = q / v`;
- число автомобилей на связи `N = k * L`;
- граничные потоки — из топологии, на стороне организатора;
- потоки рамп — из опубликованных наблюдений рамп.

Проверяются две вещи.

1. Фундаментальная диаграмма: скорость, поток и плотность на связи не независимы. При данной плотности поток ограничен, а после критической плотности поток падает.
2. Сохранение автомобилей на шаге 5 минут:

```text
N(t+dt) - N(t) = dt * (q_in + r_on - q_out - r_off)
```

Поднять Physics отдельно от State нельзя. Раньше это было возможно: можно было подставить `k = q / v_f` или спроецировать граничные потоки на уравнение баланса и получить почти идеальный физический балл при плохом состоянии. В релизе 1.0 эти ручки закрыты.

Локально Physics не оценивается содержательно. Без истинных граничных потоков `S_LWR` садится в ноль у всех, и локальное число около 0.33 ничего не говорит о качестве. Рычаг — State, который локально считается, плюс публичный рейтинг.

### ODME, вес 0.20

Классическая обратная задача. Есть наблюдаемые счётчики на связях, есть множество путей и матрица инцидентности «путь–связь», нет наблюдаемых потоков по путям. Неизвестных больше, чем независимых измерений, поэтому нужен слабый априор `b`, который тоже опубликован.

Сдаётся один неотрицательный конечный поток на путь. `departure_time` — это токен периода, а не метка времени. В публичном релизе на сплит приходится один период. У private период объявляется вместе со скрытым сценарием, токен надо копировать из шаблона.

## Как задачи связаны

```text
наблюдения с дырами
        │
        ▼
   Task 1: восстановить State
        │
        ├── Task 3: тот же файл проверяется на физику
        │
        └── Task 4: счётчики и сеть → потоки по путям
                (от State напрямую не зависит)

   Task 2: отдельные короткие окна, свой файл
```

State и Physics — одна сдача, прочитанная дважды. Вместе они дают половину итогового веса (`0.35 + 0.15`). ODME — самостоятельная обратная задача на сети. Queue почти не делит признаки с остальными и оценивается по коротким окнам, а не по целому месяцу.

Для State, Physics и ODME организатор разрешает данные всего оцениваемого периода: это офлайн-восстановление месяца, а не пошаговый онлайн-прогноз. Для Queue окно каузально: после `T` заглядывать нельзя. Слова online и offline в описании задач относятся к доступности данных во времени, а не к формату участия. Участие удалённое.

## Что считается успехом

Успешная сдача — это один CSV без пустых ячеек, с неизменными идентификаторами и полным набором строк State, Queue и ODME. Неполный блок задачи даёт ноль за всю эту задачу, а не пропуск в среднем.

Содержательный успех — метод, который одновременно:

- заполняет пропуски лучше исторического профиля дня недели и времени суток;
- не создаёт и не уничтожает автомобили между соседними связями;
- отличает распространение уже видимой очереди от зарождения новой;
- воспроизводит счётчики, не скатываясь ни в неизменный априор, ни в дикий спрос, который идеально садится на счётчики.

Публичный рейтинг считается по `validation` (март 2031, 31 день, пять инцидентов). Финальный рейтинг — по `private` (апрель 2031, 30 дней, семь инцидентов). Месяцы порождены независимо. Совпадение двух таблиц не ожидается.
